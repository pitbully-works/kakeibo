# かけいぼ ― 夢に近づく家計簿

「面倒で続かなかった人でも続く家計簿」を目指した、ビルド不要の自己完結アプリです。
開いた瞬間に「今つかえるお金」がひと目でわかり、記録は 1〜2 タップ。将来は「資産形成総合ライフプラン」へ自然につながります。

- **ひと目でわかるホーム**：主役は「今月あと使えるお金」。
- **1〜2タップで記録**：手入力、またはレシート撮影（任意のOCRで金額を自動読み取り、いつでも手直し可）。
- **端末内だけに保存**：データは `localStorage` に保存し、外部に送信しません。
- **PWA**：ホーム画面に追加でき、2回目以降はオフラインでも起動します。

---

## 計算仕様（唯一の正）

計算は **`core.js` だけ** に置いてあります。ホーム・まとめ・連携JSONは、
すべて `core.js` の `computeMonth()` の結果を読むだけで、画面ごとに足し算をしません。

### 正式な計算式

```
使える額 = 通常収入 + 臨時収入 － 支出 － 先取り貯金 － NISA積立
```

ホームの「今月 あと つかえるお金」、まとめの「のこり」、連携JSONの
`available_to_spend` は、**必ず同じ値**になります。

### ただひとつの原則：入力口はひとつだけ

お金の出入りは、**すべて「記録」から**入れます。設定には持ちません。

- 収入 … 💴 通常給与／✨ 臨時・賞与／🎁 贈与／🐷 その他臨時
- 支出 … 固定費（🏠 家賃・💡 電気・🔥 ガス・🚰 水道・📱 通信・🔁 サブスク・🛟 保険・📦 その他固定費）も、
  変動費（🥕 食費・🍜 外食・🧴 日用品・🚃 交通・🎨 趣味・🏥 医療・🎁 交際・🐷 その他）も、同じ「記録」

**同じ金額を2か所に書ける作りにしない。だから二重計上が起きません。**

### 毎月固定の印（🔁）

金額の下にある「🔁 毎月固定」をオンにすると、その記録に印が付きます。
**設定に予定額を持つのではなく、記録1件ごとの印**なので、入力口はひとつのままです。

- 印を付けても**金額は1円も変わりません**。支出として同じように引かれます
- 変わるのは3つだけ：まとめの内わけ表示／月末の予測／連携JSONの `fixed_cost`
- 収入に切り替えると印は落ちます（固定費は支出だけの考え方のため）
- オフのときは `recurring` のキーごと持ちません（保存を軽くするため）

### 先月の🔁を、今月へまとめて入れる

まとめ画面に「🔁 先月の毎月固定が N件 あります」というカードが出ます。
押すと、先月の🔁付きの記録を今月へ写します。家賃を毎月打ち直さずに済みます。

- **金額は先月と同じ**で入ります。電気代のように額が変わるものは、入れたあとで直してください
- 日付は**先月と同じ日**。その月に無い日（1/31 → 2月）は月末へ丸めます
- **今月にすでに同じカテゴリの🔁があれば入れません**。金額がちがっても入れません。
  2件に増やすより、1件を直してもらうほうが安全なためです
- 入れるものが無くなると、カードは消えます（二重に押せません）
- メモは写しますが、写真は写しません
- 入れる前に確認が出ます。保存に失敗したら**1件も増やさずに元へ戻します**

### 「その他」は1つだけ

支出カテゴリのうち 📦（旧「その他固定費」`fixother`）は、
🐷「その他」と名前が重なって紛らわしいため、**選択ボタンには出しません**。
ただしキーは `EXP_CATS` に残してあるので、
**過去に 📦 で記録したものは、これまでどおり表示・集計されます**（勝手に化けません）。
選べるのは `EXP_PICK_CATS`（`hidden` が付いていないもの）だけです。
予定額と実績を突き合わせる仕組みも、置き換えのルールも要りません。

固定費と変動費の区別は、まとめ画面の内わけ表示のためだけにあります。
どちらも同じように支出として引かれます。

### 設定に残すもの

「まだ出ていないお金」だけです。

- 先取り貯金（月・予定額）
- NISA積立（月・予定額）
- 夢・目標

どちらも入金確認をしていないため、**予定額**として扱います。
ホームの表記も「先取り貯金・NISA積立の予定額を除いています」で統一しています。

### 給与を記録していない月

収入0として扱い、ホームは「使えるお金」ではなく「今月つかった金額」を表示して、
給与の記録をうながします（マイナスの大きな数字を出さないため）。

```json
{
  "schema_version": "2.2",
  "country_code": "JP",
  "base_currency": "JPY",
  "year_month": "2026-07",

  "income_regular": 290000,
  "income_regular_basis": "actual",
  "income_regular_recorded": true,
  "income_extra": 50000,
  "income_actual_total": 340000,
  "income_net": 340000,

  "fixed_cost": 98000,
  "fixed_cost_items": [
    { "key": "rent", "name": "家賃・住居", "amount": 60000 },
    { "key": "power", "name": "電気", "amount": 12000 }
  ],
  "variable_spend": 20000,
  "spend_total": 118000,

  "planned_set_aside": 73000,
  "accounts": [
    { "type": "CASH_SAVINGS",    "local": "貯金", "basis": "planned", "planned_contribution": 40000 },
    { "type": "TAX_FREE_INVEST", "local": "NISA", "basis": "planned", "planned_contribution": 33000 }
  ],

  "available_to_spend": 149000
}
```

**2.1 からの変更点（ライフプラン側の読み取りを直す必要があります）**

| 旧 (2.1) | 新 (2.2) | 理由 |
| --- | --- | --- |
| `fixed_cost` は常に 0、`variable_spend` は支出の全額 | `fixed_cost` は「🔁 毎月固定」の印が付いた記録の合計、`variable_spend` はそれ以外。`fixed_cost_items` に項目別 | 記録1件ごとの印ができたので、固定費を実績として渡せるようになった |

`fixed_cost + variable_spend = spend_total` は変わりません。
印を1つも付けていなければ `fixed_cost` は 0 で、2.1 と同じ値になります。

**2.0 からの変更点（2.1 で入ったもの）**

| 旧 (2.0) | 新 (2.1) | 理由 |
| --- | --- | --- |
| `income_net` は設定の手取りのみ | `income_regular` / `income_extra` / `income_actual_total` に分離。`income_net` は実収入合計。すべて記録した実績 | 臨時収入が抜けていた／設定と記録の二重入力をやめた |
| `fixed_cost` は設定値のみ | 設定の固定費を廃止し、記録だけを入力口にした | 設定と記録の二重入力をやめた |
| `accounts[].contribution` | `accounts[].planned_contribution` ＋ `basis: "planned"` | 実績と誤解される名前だった |

`type`（汎用の資産クラス）は既存ライフプランアプリと共通です。

## レシートの読み取り

**撮る → 枠で囲む → 読み取る** の3ステップです。撮っただけでは読み取りません。

1. 「📸 レシートを撮る」で、合計の行に近づけて撮影
2. 白い枠を動かして、合計の金額だけを囲む
3. 「🔍 この枠の金額を読み取る」を押す

### 枠は3種類を自動で試す

利用者が合わせた枠から、**そのまま／上下左右5%広げ／上下左右10%狭め** の3つを自動生成します。
枠が少しずれていても拾えるようにするためで、いずれも画像の外にはみ出しません。

### 画像処理の候補

グレースケール＋弱いコントラスト補正／シャープ化／大津の二値化／適応的二値化。

反転の判断は `core.js` の `prepareForOcr()` の中**1か所だけ**で行います。
背景が暗い（白抜き文字）ときに1回だけ反転し、Tesseractへ渡す画像は常に
「明るい背景・暗い文字」になります。無条件に反転する候補は持ちません（二重反転の防止）。

### 段階式（最大9回、取れたら即終了）

| 段階 | 内容 | 回数 |
| --- | --- | --- |
| 1 | 通常枠 × ゆるい補正・大津 | 2 |
| 2 | 広げ枠・狭め枠 × 大津、通常枠 × 適応的 | 3 |
| 3 | シャープ化・適応的・反転など | 4 |

打ち切る条件は **「異なる読み取り実行で同じ金額が2回以上出たこと」だけ** です。
Tesseractは誤読にも高い信頼度を付けるため、1件だけの結果では——信頼度がいくら高くても——打ち切りません。
切り抜き画像は組み合わせごとに1回だけ作って使い回します。

### 先頭の桁が欠けたときの補正

「¥3,555」を「555」としか読めないことがあります。
そのままだと候補が 555 / 665 / 655 のようになり、正解が出てきません。

手がかりは**カンマ**です。カンマが見えているなら、その金額は4桁以上のはず。
そこで次の順で扱います。

1. 3桁の候補で、直前にカンマの痕跡がある → 「先頭が欠けている」と判断
2. 先頭の数字が文字として残っていれば（例：`3, 555`）それを使う
3. 残っていなければ、**その1文字がある場所だけを細い帯として切り出し、
   数字1文字として読み直す**（追加の読み取りは最大1回）
4. 読めた数字1つだけで候補を作る。**1〜9を総当たりして候補を増やすことはしない**
5. 読めなければ候補を作らない

帯の場所は、文字の位置（`col`）と行の長さから1文字ぶんの幅を見積もって決めます。

補正で作った候補には `source: "reconstructed"` の印が付き、信頼度は60を上限に抑えられます。
**この候補が1位でも自動入力はしません**。必ず利用者に選んでもらいます。

### 候補の採点

多数決だけでなく、次を合わせて0〜100点を付けます。

- 読み取り信頼度（最大40点）
- 複数の枠・処理で同じ金額が出た回数（最大30点）
- カンマの位置が自然か（最大15点／壊れていれば0点）
- OCRが返した文字列の中で中央寄りに現れたか（最大10点）
  ※ 画像上の座標ではありません。bbox を使っていないため画像内の位置は分かりません。行の中ほど・行内の中ほどに現れた数字をわずかに優遇する弱い手がかりです
- 1円以上999,999円以下（範囲外は0点）
- 合計らしい手がかり（カンマ・¥・￥・円・合計・TOTAL）がある（＋10点）
- カンマが見えているのに3桁のまま（桁が欠けている疑い）（−40点）
- 補正で作った候補（−8点）

**最高点が60点以上で、2位と12点以上の差**があれば自動入力します。
それ以外は自動確定せず、上位**5件**までをタップできる候補ボタンとして出します。
候補をタップしても金額が入るだけで、保存はされません。従来どおり「記録する」で確定します。
候補が1件も無ければ、これまでどおり手入力できます。

### 解像度

画面表示・保存は縮小版、読み取りは長辺3500pxの高解像度版をメモリ内だけに持ちます。
枠は0〜1の比率なので、どちらの画像でも同じ範囲が切り出せます。
高解像度版は保存しません。**読み取りが終わっても解放しません**——枠を直して2回目を読み取るとき、
表示用(1600px)に落ちてしまうためです。解放するのは次の4つの場面だけです。

1. 記録シートを閉じた時
2. 写真を削除した時
3. 新しい写真に置き換えた時（新しい版を入れる前に古い版を解放）
4. **記録を確定した時**＝`localStorage` への保存が成功した直後

4つ目は「保存を試みた時」ではありません。保存に失敗すると記録シートは開いたままになるため、
そこで手放すと、枠を直して読み直したときに表示用画像へ落ちてしまいます。
そのため解放は次の2か所、いずれも `save()` が成功した**直後**に置いています。

- 最初の保存が成功した時
- 容量超過で写真を外し、再保存が成功した時

両方とも失敗して記録を巻き戻す場合は、高解像度版を維持したままシートを残します。

読み取り中に作る加工画像は `readCrop()` のローカル変数なので、関数を抜ければ参照が消えます。

## 今日やることカード

ホームの「あと つかえるお金」の下に、**最大2件**だけ出ます。
`core.js` の `todayTasks(state, today)`（純粋関数）が組み立て、押すと行き先へ移るだけで、
記録は書き換えません。済んだ項目は自動で消えます（チェックを付ける操作は要りません）。

出るもの（上から優先）

| やること | 出る条件 | 押すと |
| --- | --- | --- |
| 🔁 先月の毎月固定がまだ | 先月の🔁が今月に入っていない | まとめ画面（まとめて入れるカード） |
| 💴 今月の給料がまだ | 先月までに記録した**給料日を過ぎている** | 記録シート（収入・通常給与） |
| 🧾 記録がとだえている | 最後の支出から**3日以上** | 記録シート |
| 📖 今日の日記がまだ | **続けている人**だけ（今日を除く14日で3日以上） | 日記 |
| ❤️ 今日の体重・血圧がまだ | 同上 | 健康 |

### 催促しない相手を決めておく

やることカードは、放っておくと「使っていない機能の宣伝」になります。そこで：

- **給料の履歴が無い人**には、給料を催促しません（はじめて開いた人を追い立てないため）
- **支出の記録が1件も無い人**には、とだえを催促しません
- **日記・健康を続けていない人**には、催促しません
- やることが1件も無ければ、**カードごと出しません**

## 分析タブ（詳細分析）

まとめ画面の上部で「今月」と「📈 分析」を切り替えます。
分析は**見るだけの画面**で、記録や設定を書き換えません。

計算は `core.js` の `analyzeMonth()`（純粋関数）が一括で返し、画面はそれを描くだけです。
月の合計は必ず `computeMonth()` から取るので、ホーム・まとめと必ず同じ金額になります。
**「今日」は引数で渡します**（時計を読まないので、テストでいつでも同じ結果を再現できます）。

### 出るもの

| ところ | 中身 |
| --- | --- |
| 気づき | ことばにした要点を最大5件（⚠️ 注意／🌱 よい調子／💡 事実） |
| つかうペース | これまで・1日あたり・月末の予測。累計の線と「予算のペース」（点線）を重ねたグラフ |
| ○か月の推移 | 直近6か月の収入（緑）と支出（赤） |
| 先月とくらべる | カテゴリ別に 当月・先月との差・支出にしめる割合・過去3か月平均 |
| 曜日のくせ | 曜日ごとの支出合計 |

### 決めごと

- **つかってよい額 ＝ 収入 － 先取り（予定額）**。ホームの式と同じ形です
- **月末の予測 ＝ 毎月固定（実績）＋ それ以外 ÷ 経過日数 × 月の日数**。
  家賃のような毎月固定を日割りすると、月初だけ予測が跳ね上がるためです。
  印を1つも付けていなければ、これまでどおり「支出 ÷ 経過日数 × 日数」と同じ式になります
- ペースは**経過日数までに記録した分**で見ます。月の後ろの日付を入れた記録を、
  まだ使ったことにしないためです（`spendTotal` は当月ぜんぶ、`spentSoFar` は今日まで）
- 給与を記録していない月は、使いすぎの判定をしません（`over` は `null`）。
  代わりに「給料を記録すると、ペースが分かります」と伝えます
- 過去3か月の平均は、**記録のあった月だけで割ります**。
  使いはじめた月に平均が薄まって「先月より激増」に見えるのを防ぐためです
- 先月に記録が無い項目を「ふえた」とは言いません（はじめての項目、と表示します）
- 推移のグラフに先取り・のこりを出しません。先取りは**今の設定の予定額**であって、
  過去の月に当てはめると事実と違う額になるためです
- 曜日は UTC で読みます（端末のタイムゾーンで曜日がずれないようにするため）

## 更新の届き方（Service Worker）

iPhone の Safari は `sw.js` 自体をキャッシュすることがあり、放っておくと
古い画面・古い `core.js` が残り続けます。そこで登録側と `sw.js` の両方で対策しています。

### 登録側（index.html）

```js
// 登録する前に「すでに制御されていたか」を控える
const hadController = !!navigator.serviceWorker.controller;

const registration = await navigator.serviceWorker.register("./sw.js", {
  updateViaCache: "none"      // sw.js を必ず取り直す
});
await registration.update();  // 登録直後に更新確認

let refreshing = false;
navigator.serviceWorker.addEventListener("controllerchange", () => {
  if (!hadController) return;  // 初回登録。更新ではないので読み直さない
  if (refreshing) return;      // 無限に読み直さないための印
  refreshing = true;
  window.location.reload();    // 新しい版に切り替わったら1回だけ読み直す
});
```

`controllerchange` は**初回登録のときにも発火します**。そのまま読み直すと、
初めてアプリを開いた人に余計なリロードが1回入ります。
登録前の `navigator.serviceWorker.controller` を見て、
「もともと制御されていた＝更新である」場合だけ読み直します。

### sw.js の方針

| 対象 | 方式 |
| --- | --- |
| 画面（index.html・ナビゲーション） | **ネットワーク優先**。失敗時のみキャッシュ |
| アプリのコード（`.js` / `.html`） | **ネットワーク優先**。失敗時のみキャッシュ |
| 変わらない部品（アイコン・manifest） | キャッシュ優先＋裏で取り直し |

`core.js` をキャッシュ優先にすると、更新した直後の1回だけ古い版が読み込まれます。
画面と足並みを揃えてネットワーク優先にすることで、これを解消しています。
オフラインでの起動はどちらの場合も維持されます。

キャッシュ名（`kakeibo-v11`）を変えると、`activate` のときに古いキャッシュを丸ごと捨てます。
**アプリを更新したら、この版数を必ず上げてください。**

## カレンダー

下部メニューの「📅 カレンダー」から、月ごとに記録を見渡せます。

- 月グリッド表示（前月/次月に移動）。記録のある日に色ドット（支出=赤・収入=緑・日記=黄・健康=青）
- 日をタップ → その日の支出・収入・日記・健康をまとめて表示
- 支出/収入の項目をタップ → 記録編集シート、日記/健康の項目 → それぞれのページへ
- 集約は `core.js` の `dayDetail(state, date)`（純粋関数）が担う。旧形式の日記も読める

## 健康記録

下部メニューの「❤️ 健康」から、体重・血圧を記録できます。

- 1日1件（同じ日にもう一度記録すると上書き）
- 体重の折れ線グラフ、血圧（上/下）の折れ線グラフを、日/週/月で表示
- データは `state.health`（`{ "YYYY-MM-DD": {weight,bpHigh,bpLow} }`）に保存。
  家計簿(`state.tx`)とは完全に別領域で、計算・保存には影響しない
- 将来 体温などを足すときは `core.js` の `HEALTH_FIELDS` に1行足すだけ
- バックアップの書き出し/読み込みにも含まれる（health の無い旧バックアップも読める）

正規化(`normalizeHealthEntry`)で、数値でない・範囲外・未入力の項目は捨てる。
保存に失敗したら健康データは記録前へ完全に戻す。

## 心拍数（カメラ／PPG・β版）

下部メニューの「💓 心拍β」から、**背面カメラとライトで心拍数を測れます**。
指の中を通る光の量が、脈に合わせてわずかに変わることを利用しています（PPG）。

**医療機器ではありません。** 画面には常に
「この測定値は健康管理の参考値です。診断・治療目的では使用できません。」を出します。

### 測り方と決めごと

- 測定は **60秒**。最初の **10秒は準備時間**で、計算には使いません
- 解析は 10秒の窓を 5秒ずつずらして **9窓**。窓ごとに自己相関で周期を求め、
  中央値から離れた窓を捨て、残りの平均を心拍数とします
- 解析する区間は「10秒〜60秒」に**固定**します。測定のわずかな長さの差で
  窓が8個になったり9個になったりしないためです
- 数の決め方は **`core.js` の `analyzePulse()`（純粋関数）だけ**にあります。
  画面はカメラの制御と表示だけを持ちます

### 測定品質（★5段階）

「信頼度」とは呼びません。**測定品質**で統一しています。

| 表示 | 意味 |
| --- | --- |
| ★★★★★ | とても良好 |
| ★★★★☆ | 良好 |
| ★★★☆☆ | 普通 |
| ★★☆☆☆ | やや不安定 |
| ★☆☆☆☆ | 再測定推奨 |

### 正式な記録として保存する条件

次を**すべて**満たしたときだけ履歴に残します。

- 採用窓 **6/9 以上**
- **25fps 以上**
- 測定品質 **★3（普通）以上**
- 途中で指が離れていない
- 心拍数 **35〜200bpm**

満たさないときは保存せず、
**「測定品質が不足しています。安静にして再測定してください。」** と出します。

**ライトの点灯は条件に入れません。** 点けられる端末では点けて信号を強くしますが、
ライトを制御できない端末・ブラウザでも測定は続け、
保存してよいかは **測定品質・採用窓・fps** だけで判断します。
ライトのON/OFFは、あとから見返せるよう記録には残します。

### 保存する内容と、見せ方

保存するのは**数値だけ**です。映像・画像・カメラのフレームは
**保存も送信もしません**（`fetch`／`XHR` を使いません）。

| 保存する項目 | 通常の画面 | 詳細を開くと |
| --- | --- | --- |
| 心拍数 / 測定日時 / 測定品質 | ○ | ○ |
| 採用窓 / ばらつき / fps | — | ○ |
| カメラ解像度 / ライト / 使用端末 / 測定状態 | — | ○ |

データは `state.pulse`（配列・1日に何件でも）。家計簿とは別領域で、
計算・保存データには影響しません。CSV出力には**全項目**が入ります。

### できること

- 健康ページの「心拍数」カードに、最新の 心拍数・日時・測定品質を表示
- 健康ページに **日／週／月** で切り替えられる折れ線グラフ
  （1日に何度か測った日は、その日の平均を1点にします）
- 履歴の **編集**（心拍数・測定状態）・**削除**・**CSVエクスポート**
- 測った心拍数を、そのまま **健康記録へ入れる**ボタン
  （体重・血圧と同じ入れ物。1日1件で上書き。電卓の「答えを家計簿に記録する」と同じ考え方）

### カメラの後始末

**測定終了・中止・画面移動・アプリの切り替え・閉じる**——どの場合でも
`pulseStopAll()` を必ず通り、ライトを消し、カメラを止め、時計を止めます。

## 日記

下部メニューの「📖 日記」から、日付ごとに日記を記録・編集できます。

- 1日1件（過去の日付をタップすると、その日の日記を直せる）
- 本文を空にして保存すると、その日の日記は消える
- データは `state.diary`（`{ "YYYY-MM-DD": "本文" }`）。家計簿とは別領域
- 表示は必ずエスケープ（HTMLを書いても生タグにならない）
- バックアップに含まれる（diary の無い旧バックアップも読める）
- 保存に失敗したら記録前へ完全に戻す
- **写真を1枚添付できる**（撮影・写真ライブラリのどちらからも選べる）
  - 保存前に縮小。容量オーバーなら写真だけ落として本文は残す
  - 写真は画像の data URL のみ受け入れる（XSS対策）
  - データは `{ "YYYY-MM-DD": { text, photo? } }`。**旧形式（本文の文字列だけ）も自動で読める**

## バックアップ

設定画面から書き出しと読み込みができます。

- **書き出す**：`{ version, exportedAt, settings, tx }` の形のJSONを保存
- **読み込む**：`.json` を選ぶと、上書きの確認のあとに復元

読み込むファイルは「他人が作ったかもしれないもの」として扱い、`core.js` の
`parseBackupJson()` → `normalizeBackup()` で必ず正規化してから取り込みます。

- JSONとして読めない／形が違う → 中断し、現在のデータは一切変更しない
- `settings` がオブジェクトでない、`tx` が配列でない → 中断
- 金額は有限の0以上の整数へ（負数は絶対値、小数は切り捨て、上限で頭打ち）
- 日付は実在する `YYYY-MM-DD` のみ（`2026-02-31` は除外）
- `type` は `income` / `expense` のみ、未知のカテゴリは「その他」へ
- メモは上限文字数で切る、写真は画像の data URL のみ受け入れる
- 保存に失敗したら、読み込み前のデータへ完全に戻す

**旧形式（version が無い、`state` をそのまま書き出したもの）も読み込めます。**

## 保存について（端末内・容量の話）

データは `localStorage` に保存します。**保存できるのは端末あたりおよそ5MB**です。
スマホの写真は1枚で数MBあるため、そのまま持つと1〜2枚で上限に達し、
保存が失敗して「記録したのに残らない」状態になります。そのため：

- 撮影した写真は、画面表示用に長辺 **1600px** まで縮めます
- 読み取り用には長辺 **3500px** の高解像度版を**メモリ内だけ**に別途持ちます（保存しません）
- 保存するときは、さらに長辺 **900px** / JPEG品質0.6 まで縮めます（1枚おおよそ100KB前後）
- それでも入りきらない場合は、**写真だけを諦めて記録は必ず残し**、その旨を画面に出します
- どうしても保存できないときは、変更を元に戻したうえで理由を表示します（黙って失敗しません）
- せってい画面に使用量を表示し、「写真をすべて消す（記録は残ります）」で空きを作れます

## テストが効いているかの確認（自作の mutation test）

テストを増やしても、それが本当に不具合を捕まえられるとは限りません。
そこで **ソースをわざと壊して、テストが落ちるかどうか** を確かめる簡易な仕組みを自作しました。

```bash
node run-mutations.js
```

**これは mutation testing 全体を網羅するものではありません。**
Stryker のような本格的なツールのように、あらゆる演算子・条件・戻り値を機械的に変異させる
わけではなく、**壊れると困る重要な178パターンを手作業で選んで列挙したもの**です。
選んだ範囲の外に穴が残っている可能性はあります。

対象にしているのは、拡大枠の無効化、はみ出し防止の削除、反転の二重適用、
読み取り後に高解像度画像を捨てる、保存の成否が出る前に解放する、保存の失敗を握りつぶす、
キャッシュの版数を上げ忘れる、古いキャッシュを消さない、といった、
測定を止めてもライトが消えない、心拍数の保存条件がゆるむ、解析の窓の数が変わる、といった、
この家計簿で実際に起きた／起きうる壊れ方 **178パターン** です。

結果は `MUTATION-REPORT.md` に書き出されます。1件でも検出できなければ不合格として終了します。

合否の判定には `node --test` の**終了コード**を使います。
出力の表示形式（tap / spec）は Node のバージョンや実行環境で変わるため、
文字列を読み取って判定すると環境によって壊れます。

実際にこの仕組みで2件の穴が見つかり、テストを追加して塞ぎました
（単独結果での早期終了と、保存失敗時の巻き戻し）。

## テストの実行

追加インストールは不要です（Node 18以降の標準機能だけを使います）。

```bash
node --test
```

### GitHub Actions（push のたびに自動実行）

`.github/workflows/test.yml` により、`main` への push と pull request で自動実行されます。
リポジトリの **Actions** タブで結果（緑／赤）を確認できます。

実行される内容は次の3つで、**どれか1つでも失敗すれば赤**になります。

1. `node --test` … 通常テスト
2. `node run-mutations.js` … 自作 mutation test（見逃しが1件でもあれば失敗）
3. `git diff --exit-code` … mutation test がソースを元に戻せているかの確認

外部APIやシークレットは使いません。`package.json` が無いため `npm test` ではなく、
Node 標準のテストランナーを直接呼んでいます。
結果の件数と mutation test のレポートは、実行画面のサマリーに表示されます。
